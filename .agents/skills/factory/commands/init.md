`/factory init [--title T]`: set up a repo that was created from this one as a template, or that got the factory through `apm install` and has no `.eridanilabs/autofactory/board.json`, so the factory works on **its** issues, board and audit log, not the template's. Run it once, before any other `/factory` command. With no `board.json` on `main`, it builds one from the built-in defaults; with a template's, it rewrites the template's references. Until its PR merges, every `board.mjs` command stops with `✗ .eridanilabs/autofactory/board.json targets <template>, but this checkout's origin is <this repo>…`. When start-up stops with that error, tell the user to run `/factory init`, or to merge the open `factory/init` PR. If start-up instead fails because `.eridanilabs/autofactory/board.json` is missing, the repo has no `board.json` yet: tell the user to run `/factory init`. That shows up as either a `no such file` (`ENOENT`) error that names it or `fatal: pathspec '.eridanilabs/autofactory/board.json' did not match any files`. That pathspec error isn't the old-path one in [start-up](#0-start-up-every-command) step 3 (`pathspec 'factory/board.json'`), so don't send the user to `git pull` for it. If start-up fails with `refresh: origin/main has no board.mjs at …`, the factory isn't installed on `main` yet: tell the user to commit the `apm install` output to `main`, then run `/factory init`.

1. Pass `--title` only if the user names the board. The template's run records stay behind: they live on its `factory-log` branch, which a repo made from the template doesn't copy.
2. Run it from any checkout of the repo. It works from a freshly fetched `origin/main` in a temporary worktree and leaves this checkout as it is:

   ```bash
   node $B init [--title "<board title>"]
   ```

   It creates the board, pushes the changes to the branch `factory/init`, and opens a PR into `main` (`chore(factory): set up the factory for <owner>/<repo>`). The new `board.json` keeps only the board's `project.number`; its ids go into this checkout's git-ignored cache, `.eridanilabs/autofactory/cache/project.json`. The same commit adds the Factory request form (`.github/ISSUE_TEMPLATE/factory-request.yml`) and a `.eridanilabs/autofactory/runs/` line in `.gitignore` when `main` lacks them. It never replaces ones `main` already has: an existing form only gets the template's references rewritten, like any other file, and an existing `.gitignore` only gets the line appended if it's missing. If `main` still has the old `factory/board.json`, the same commit moves it to `.eridanilabs/autofactory/board.json` with `git mv`, so its history follows.
3. Show its output: the files it rewrote or added, and any request form it skipped because something is in its path, and the PR's URL. Pass each `· skipped` line on to the user. If it says `nothing to do`, this repo is already set up (if it also prints a `git mv` line, `main`'s config is still at the old path: show the user that line); if it says the init PR is already open, show that PR. Either way, stop there.
4. Tell the user to review and merge the PR (a human merges it, never the factory), then run `/factory`. After the merge, start-up's refresh caches the new board's ids in each checkout that runs it.

Init does no run work: no issue, no card, no agents. If it fails, report the error and stop.
