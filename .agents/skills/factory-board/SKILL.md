# factory-board

The board is how a person watches the factory. Each feature is one issue, one card. The card's **Status** is the stage. The `/factory` orchestrator is the only thing that moves cards; agents never touch the board.

Everything runs through one zero-dependency script, so board changes are deterministic and verified:

```bash
B=.github/skills/factory-board/board.mjs
[ -f "$B" ] || B=.agents/skills/factory-board/board.mjs
```

`apm install` puts the script under `.agents/skills/`, and only branches cut before the move to APM still keep it under `.github/skills/`.

`board.mjs` reads its config from `.eridanilabs/autofactory/board.json` and keeps local run records in `.eridanilabs/autofactory/runs/`. `board.json` holds only the board's `project.number`; the board's ids (`id`, `url`, `number`, `statusFieldId`, `statusOptions`, `textFieldIds`) live in a git-ignored cache in each checkout, `.eridanilabs/autofactory/cache/project.json`, whose folder holds its own `.gitignore` of `*`. A command that needs them reads the cache first, then a `board.json` `project` block from before the cache (which seeds the cache, with no network call), then looks the live board up, read-only, by `owner` and `project.number` (or by `title` when there's no number) and caches it. A cache that's missing a column or text field from `board.json`, or holds another board's number, is looked up again once. For one release, a repo set up before that move still works: when `.eridanilabs/autofactory/board.json` is missing, it falls back to the old `factory/board.json`, and `refresh` (or an `init` with nothing to do) prints the one-line `git mv` that moves it.

## `node $B ensure`: make sure the board exists

Run it at the start of every `/factory` command. It's safe to rerun, and it changes only what's missing:

- Finds the open project numbered `project.number` in [board.json](../../../apm_modules/eridanilabs/autofactory/.eridanilabs/autofactory/board.json). With no number (as `init` plans it), it finds the project titled `title`, or creates it. That board must be this repo's: linked to `repo`, or titled `title` and linked to no other repo. When there's no open board with that number, or it's another repo's board (`✗ <owner>'s board #N, …, isn't this repo's: it's titled "…" and linked to other/repo; …`), it stops before changing anything and names the fix: `✗ <owner> has no open board #N, …; its board titled "<title>" is #M, so open a PR that sets `project.number` to M`. Every command that looks the ids up stops with the same message, so they all use one board.
- Makes it **private** and links it to `repo`.
- Sets the Status columns to `statuses` (in order). It keeps existing option ids so cards stay put, and **refuses to remove a column a card still uses**.
- Adds text fields `Agent`, `Checkpoint`, and `Human request`.
- Adds the `factory` label and the extra `labels` in `board.json` (`from-review`, `needs-triage`, `needs-info`, `external`, `rejected`, `factory:stop`, `next`, `needs-split` (added even when an older `board.json` doesn't list it), the severity labels `blocker` and `nit`, and the review-type labels `code`, `security`, `ops`, `ux` and `ui-design`). It never redefines existing labels, and never adds a label per column: a card's column lives only in its Status.
- Makes the board view (`view`, `Factory floor`, grouped by Status) the first view, so the board opens on it. Its fields are Title, Assignees, Status, Labels, Linked pull requests, Milestone and the text fields. On a new board, it first creates the Plan view and a table named `All cards` with the fields of GitHub's untouched first view (`View 1`, a table), then turns View 1 into `Factory floor` in place. When an untouched View 1 sits before an existing `Factory floor`, the two swap: the old `Factory floor` becomes `All cards` (a table with View 1's fields), then View 1 becomes `Factory floor` (`~ made Factory floor the first view (saved filters, sorts and slices stay with each view, not its name); the old Factory floor is now All cards`). Each step can be retried: a run that stops part-way leaves an untouched View 1, and the next run finishes the job. When someone has changed the first view, or `All cards` is already taken, `ensure` never writes to it: it creates `Factory floor` if it's missing, and prints `· Factory floor isn't the first view; drag it to the left in the Project to open the board on it`, which isn't logged. A view create is logged only when GitHub's response holds the new view; a failed `All cards` or `Factory floor` create stops `ensure` before View 1 is changed.
- Adds a **Plan view** (`planView` in `board.json`, `Plan` by default, or when the key is missing): a table grouped by Milestone, showing Title, Status, Milestone, Labels, Assignees and Linked pull requests, for planning work in phases. Set `planView` to `null` to skip it. A view with that name that already exists is never changed, whatever its layout. The Plan view is optional: when creating it fails, `ensure` prints `⚠️ could not create plan view "Plan": <reason>; set "planView": null in board.json to skip it` and carries on.
- Two `ensure` runs at the same moment can each create a Plan or All cards view. Delete the extra tab by hand in the Project; `ensure` never deletes views.
- Creates the [audit log](#the-audit-log) branch `factory-log` if it's missing, plus a ruleset that blocks deleting or force-pushing it.
- Caches project and field ids in this checkout's `.eridanilabs/autofactory/cache/project.json`, never in `board.json`, so there's nothing to commit.

To change the columns (the full steps are in [Renaming a column](../../../apm_modules/eridanilabs/autofactory/docs/board-json.md#renaming-a-column), `docs/board-json.md` in the autofactory repo):

- Every column in `statuses` has a fixed `key` and `role`: never change them. Edit only its `name` (and its `color` or `description`).
- Empty the column first if it has cards, or `refresh` fails with `cards still use status <old name>` once the rename merges.
- Merge the rename to `main`, then run `refresh` (any `/factory` start-up runs it), then `git pull --ff-only` in each checkout on `main`. `refresh` never reads your checkout, so a local edit alone changes nothing. Until then, every command that reads the board's ids warns about the column.
- The `/factory` orchestrator still moves cards by the default names (`Spec`, `Build`, `Review`, `Approve`, `Needs human`, `Done`, `Backlog`), so renaming one of those breaks its moves until `move` accepts a key.

**Every command except `init` refuses to run** (exit `1`, `✗ .eridanilabs/autofactory/board.json targets <repo>, but this checkout's origin is <origin>…`) when `repo` in `board.json` isn't the repo that `origin` points at (`remote.origin.url`, compared without case). A repo made from the template starts with the template's `board.json`, so without this check it would move cards on the template's board and write to the template's issues and audit log. The fix is to run [`init`](#node-b-init---title-t-set-up-a-repo-made-from-the-template) and merge its PR.

## `node $B refresh`: cache this checkout's board ids

The `/factory` orchestrator runs this at start-up, from any checkout. It never touches the caller's tracked files (its `HEAD`, branch, index and working tree stay the same); only its git-ignored cache and the `origin/*` remote-tracking refs change.

1. `git fetch origin`, then `git worktree add --detach <tmp>/main origin/main`.
2. Runs that worktree's own `board.mjs ensure` there, so it reads `main`'s `.eridanilabs/autofactory/board.json`.
3. Copies the worktree's cache into this checkout's cache. If the worktree has no cache (an older `board.mjs` on `main` writes the ids into its `board.json` instead), it takes them from that file's `project` block. It never commits or pushes. If `main` has only the old `factory/board.json`, that's the file it reads, and it prints the `git mv` that moves it; it never moves the file itself.

The temporary worktree is removed (`git worktree remove --force`) and its temp dir deleted every time, whether it succeeds or fails. It prints `✓ board ids cached (updated)`, or `(unchanged)` when the cache already held those ids. It takes no arguments.

**A stale id.** If a command in some checkout fails on an id the board no longer has (its project or a field was recreated), run `node $B refresh` in that checkout, or delete its `.eridanilabs/autofactory/cache/` folder so the next command looks the ids up again. Rebasing doesn't help: the cache isn't in git.

**Stale-checkout warning.** After that, it runs `git diff --quiet HEAD...origin/main -- .agents/skills .eridanilabs/autofactory/board.json` in your checkout. If `main` changed either since this checkout's merge base, it prints a one-line warning on stderr: `! origin/main has newer … than this checkout: run git pull --ff-only in this checkout`. Stdout is unchanged, and it still exits `0`. If the check can't run (no `origin/main`, say), it prints nothing.

## `node $B init [--title T]`: set up a repo made from the template

Run it once, by hand, from any clone of a repo created from this one with **Use this template**, or of a repo that got the factory through `apm install` and so has no `.eridanilabs/autofactory/board.json`. It sets up the new repo's board, then opens a PR that points the factory at the new repo. Like `refresh`, it never touches the caller's checkout (its `HEAD`, branch, index and working tree, even uncommitted changes), and it creates no local branch:

1. Needs an `origin` that's a GitHub URL (read from `remote.origin.url`). Runs `git fetch origin` and reads `main`'s `.eridanilabs/autofactory/board.json` (or, failing that, the old `factory/board.json`) from `origin/main`. If that already targets `origin`, it prints `✓ … nothing to do` and exits `0`, so running it in the template itself, or after the init PR merged, changes nothing; when `main`'s file is at the old path, it also prints the `git mv` that moves it. If `origin/main` has no `.eridanilabs/autofactory/board.json`, it carries on with the built-in defaults.
2. If the branch `factory/init` is already on `origin`, it prints the open PR from it (`✓ the init PR is already open: <url>`) and exits `0`. With no open PR, it stops and asks you to delete the branch (`git push origin --delete factory/init`) and rerun.
3. Plans the new config: `repo` and `owner` from `origin`, `title` from the repo name (or `--title`), and no `project` ids. Every other key comes from `main`'s `board.json`, or, when there's none, from the built-in defaults (`DEFAULT_CONFIG` in `board.mjs`: the same columns, fields, labels and reviewers as the template).
4. Runs [`ensure`](#node-b-ensure-make-sure-the-board-exists) with that config. It creates the new repo's own private board, columns, fields, labels, view, `factory-log` branch and ruleset. If the owner already has an open board with that title linked to another repo, it stops before changing anything and asks for `--title`.
5. In a temporary detached worktree on `origin/main`, writes `.eridanilabs/autofactory/board.json` with only the new board's `project.number`, and caches its ids in this checkout. If `main`'s `board.json` is at the old `factory/board.json`, it first moves it there with `git mv`, so its history follows, and the PR body says so. With a template's `board.json`, it also rewrites the template's references in every tracked text file except `.gitignore`: the old board URL, `<old owner>/<old repo>`, and `` `<old owner>` ``. With no `board.json`, nothing is rewritten. The template's run records stay behind: they live on its `factory-log` branch, which a repo made from the template doesn't copy.
6. In both cases it adds what `origin/main` is missing, and never replaces what it has:
   - **`.github/ISSUE_TEMPLATE/factory-request.yml`**, the Factory request form, copied from `templates/factory-request.yml` next to `board.mjs`. A form the repo already has is kept, not replaced: with no `board.json` it stays exactly as it is, and with a template's `board.json` only its references to the template are rewritten, as in step 5.
   - **A `.eridanilabs/autofactory/runs/` line in `.gitignore`**, so the run records `records` mirrors stay out of git. It creates `.gitignore` if it's missing and appends the line if it's absent. If the line is already there, the file isn't touched.
7. Commits all of that as one commit, `chore(factory): set up the factory for <owner>/<repo>`, pushes it to the branch **`factory/init`**, and opens a PR into `main` with the same title. The PR body lists the board, says whether `board.json` was created from the defaults or rewritten from the template, and lists the rewritten files and every file it added. The worktree is removed whether this succeeds or fails.

It prints the rewritten and added files, and any request form it skipped because something is in its path (a `· skipped` line), and the PR's URL. Review and merge the PR, then run `/factory`. Until it merges, `main`'s `board.json` still targets the template (so every other command stops on the check above), or `main` has no `board.json` at all (and every other command fails because the file is missing).

If step 4 fails, nothing has been pushed: fix the cause and rerun. `ensure` is safe to rerun. If step 5 refuses because a file is in the way (`board.json` already exists, or a symlink or a non-directory is in its path), nothing has been pushed either: fix it on `main` and rerun (with the same `--title`, if you passed one), and `init` reuses the board step 4 created. If the PR can't be opened after the push, open it from `factory/init` by hand, or delete the branch and rerun. GitHub can't create a Project from a workflow's `GITHUB_TOKEN`, so this runs locally with your `gh` login, which needs the `project` scope (`gh auth refresh -s project`).

## `node $B move <issue> <Status> [options]`: move a card

| Option | Sets |
|--------|------|
| `--from <Status\|none>` | **Expected current column.** If the card is elsewhere, a person moved it: exit `3` with no writes. |
| `--agent "<who>"` | Card field `Agent`, for example `builder-app · claude-opus-5.5`. Pass `""` to clear. |
| `--checkpoint "<what>"` | Card field `Checkpoint`, for example `PR #4 @ 1a2b3c4`. |
| `--human-request <url>` | Card field `Human request` (the comment asking for a decision). |
| `--reason "<why>"`, `--next "<what>"` | Shown in the transition record only. |
| `--summary-file <path>` | Markdown that says what the stage produced (ACs, files and tests, verdict table, decision). It goes at the top of the comment. |
| `--pr <number>` | Also post the comment on this PR, and give the PR the issue's milestone (see step 3). |

One move takes about 3 seconds and does this:

1. **One read**: the issue (body, labels, closing PRs) and its card. Checks `--from`. Adds the issue to the board if it isn't there yet.
2. **Parallel writes**: Status, each card field that changed (unchanged ones are skipped), and the `factory` label (it never removes a label). Each field write returns the value it set, and those values are checked.
3. **Records, in parallel**:
   - a comment on the issue (and the PR with `--pr`): `🏭 Build → Review`, then the summary, a fields table, and a ✅ verified or ⚠️ partial receipt;
   - the [progress checklist](#progress-checklist) in the issue body, written with the same verify-and-retry as [`--into`](#--into-x-fold-a-finding-into-an-existing-issue);
   - one commit to the [audit log](#the-audit-log);
   - with `--pr`, the PR's milestone: when the issue has a milestone and the PR's is different (none or another one), `move` sets the PR's to the issue's, so a milestone's merged PRs can be listed for its release notes. It changes nothing when the issue has no milestone or the PR already has the same one, and never clears one. A failed update adds a `PR milestone: <msg>` problem: the `⚠️` line and exit `1`.

A no-op `ensure` is a single read.

### Done belongs to GitHub

The project's built-in **Item closed** workflow moves a card to Done when its issue closes. That happens when the PR merges, or when `/factory reject` closes the issue as not planned. **Done means merged, or closed unmerged when labeled `rejected`.** That workflow is the source of truth, so `move <n> Done --from <col>` doesn't fight it. `move` reads the issue's `state` and `stateReason` with its closing PRs:

| Card is in | Issue closed by a merged PR, or closed as not planned, labeled `rejected`, with no merged PR (rejected)? | What `move` does |
|------------|------------------------------|------------------|
| `Done` | yes | **auto**: writes no Status; updates fields, label, comment, checklist, and log, noting `🤖 auto-moved by GitHub` (log `auto: "github"`). For a rejected issue the note says it was closed unmerged (rejected). |
| `<col>` | yes | waits up to 30s for GitHub, then auto; if it still hasn't moved, sets Done itself and notes it (log `auto: "fallback"`) |
| anything else | either | the usual `--from` check: drift, exit `3` |

### Progress checklist

Each move (except into Backlog) rewrites one block in the issue body, between `<!-- factory:progress -->` and `<!-- /factory:progress -->`. Everything outside the markers is left alone. It ticks finished stages, bolds the current one (⏳), and notes each stage's checkpoint. Needs human appears only once it's used. The block is rebuilt from its own notes, so don't edit it by hand. The write reads the fresh body, applies the block, reads it back, and retries if another write dropped it (up to 3 writes); if it never sticks, the move reports `progress: … not saved` and exits `1`.

Exit codes: `0` verified and logged, `1` failed or partial (the comment says what's wrong; rerun the same move to repair), `2` bad usage, `3` card not where expected (logged as drift), `4` moved and verified but the log commit failed (the entry is printed to stderr; report it and carry on).

## `node $B finding <parent> <reviewer> --as sub|backlog --text "<line>" [--round r] [--pr p]`: file a review finding

Turns one reviewer finding line (`- [nit] (rule) path:line: problem. Fix: suggestion.`) into an issue labeled `from-review`. The issue body says who found it, where, and in which round and PR. The `(rule)` tag is optional; when it's there, the body gets a `| Rule | <rule> |` row under `| Severity |`.

- **Labels:** the issue also gets its severity label (`blocker` or `nit`) and its review-type label: the reviewer name without `reviewer-` (`code`, `security`, `ops`, `ux` or `ui-design`), so you can filter for, say, open `security` `blocker`s. All three are read in the same query. A missing `from-review` or severity label fails with `run board.mjs ensure`. A review-type label that doesn't exist (`copilot` for `reviewer-copilot`, `human` for `reviewer-human`) only prints a `⚠️` warning on stderr naming it, and the issue is filed with its other labels. `board.mjs` never creates that label; add it by hand if you want it. A type that names another factory label (`factory`, `from-review`, `next`, `external`, …) is never applied.

`<reviewer>` is any name like `reviewer-[a-z-]+`. That covers the factory's reviewers (the `reviewers` list in `board.json`) and outside ones that `/factory revise` files, such as `reviewer-copilot` for Copilot and `reviewer-human` for a person.

- `--as sub` makes it a **sub-issue** of `<parent>`, for findings fixed in this loop, in `<parent>`'s milestone (none when `<parent>` has none). `--as backlog` and `--into` set and change no milestone, apart from the Polish issue's own create below. The orchestrator makes sure the PR body has `Closes #x` for the resulting issue, whether it was created or folded in with `--into`.
- `--as backlog` makes it its own card in the **Backlog** column (through `move … Backlog --from none`), to be built later with `/factory <x>`.
- **The Polish issue:** a `[nit]` filed `--as backlog` with no `--into`, while a milestone is active, isn't its own card. It goes into the active milestone's one `Polish: <milestone title>` issue: the open issue in that milestone with exactly that title. If there is one, the nit is appended under its `## Merged findings` with its fingerprint marker, with the same comment and labels as [`--into`](#--into-x-fold-a-finding-into-an-existing-issue) (plus `from-review` if it lacks it, and `security` for a `reviewer-security` nit), and it prints `~ #x merged (polish) <url>`. If there isn't, it's created in the active milestone with `from-review` and the nit's severity and type labels, a short intro and the nit under `## Merged findings`, and its card goes to Backlog with next `/factory x`; it prints `+ #x created (polish) <url>`. Only an issue labelled `from-review` counts. With no active milestone, `--as sub`, a `[blocker]` or `--into`, nothing changes. Nor when the open Polish issue is `<parent>` itself or its card is busy (in Spec, Ready, Build, Review, Approve or Needs human, as groom's merge check): the nit gets its own Backlog card, so the Polish PR never closes it unfixed. A found Polish issue with no card on the board gets one in Backlog (`move … Backlog --from none`), so a move that failed after its create is repaired on the next nit or `polish`. A milestone error (two active milestones, say) exits 1 with `✗`: it never falls back to a plain Backlog card.
- **Duplicates:** a hidden fingerprint goes in the body (`<!-- factory:finding <hash> -->`), made from the reviewer, the file, and the problem text, with line numbers ignored. If an open `from-review` issue already has it, nothing is created. A fold into `#x` (with `--into`, or a backlog nit routed to a Polish issue) also checks `#x`'s own `## Merged findings` items: one with the same fingerprint, or the same problem text (normalized as the fingerprint normalizes it, whatever the reviewer, path or line), prints `= #x exists …` and changes nothing.
- **Output:** `+ #x created …`, `= #x exists …`, or `~ #x merged …` (with `--into`); `+ #x created (polish) …` or `~ #x merged (polish) …` for a Polish issue.
- **Notes aren't filed:** a `--text` that starts with `[note]` (or `- [note]`) prints a `✗` line saying notes aren't filed and exits 1, before any `gh` call.

### `--into <x>`: fold a finding into an existing issue

`finding <parent> <reviewer> --as sub|backlog --text "<line>" [--round r] [--pr p] --into <x>` adds the finding to open issue `#x` instead of creating a new one. Use it when triage says the finding duplicates or belongs with `#x`.

- **Checks first, writes nothing on failure:** `<x>` must be a positive integer, and `#x` must be open and labeled `from-review`. With `--as sub`, `#x` must also be a sub-issue of `<parent>`, so the PR that closes it still closes the finding. The orchestrator adds `Closes #x` to the PR body if it isn't there yet.
- **Idempotent:** if any open `from-review` issue already carries the finding's fingerprint, in its own marker or inside a merged item (`#x` included), it prints `= #y exists …` and writes nothing. Rerunning the same command is safe. Then `#x`'s own `## Merged findings` items are checked: an item with the same fingerprint, or a text match (the same problem text, normalized as the fingerprint normalizes it, ignoring reviewer, path and line), prints `= #x exists …` and exits 0, with no body write, comment or label change. A backlog nit routed to the active milestone's Polish issue gets the same check.
- **Merged-item format:** the finding is appended to the end of a `## Merged findings` section in `#x`'s body (the section is added if it's missing). Everything else in the body, including the progress checklist, is left byte-for-byte as it was:

  ```markdown
  ## Merged findings

  - [ ] **nit** (ux, review round 1 of #23 (PR #24)): `public/index.html:60`: <problem> **Fix:** <fix>
    <!-- factory:finding 1a2b3c4d5e6f -->
  ```

  The location comes between the source and the problem as `` `path:line`: `` (or `` `path`: `` without a line, and nothing when the finding has no path). ` (PR #…)` is left out without `--pr`, and ` **Fix:** …` when the finding has no fix. Hand-merged items with an issue number in bold (`**#27**`) are read the same way.
- **Verify and retry:** the body write reads the fresh body, appends the item, waits, and reads it back. If another write dropped the item, it backs off with jitter (about 200 ms × 2^attempt, plus up to 200 ms) and tries again, up to 3 writes. If the item still isn't there, it prints `✗ #x body not saved …`, posts no comment, and exits non-zero.
- **Best-effort, so run one at a time:** GitHub has no compare-and-swap on an issue body, so an overwrite that lands after the read-back still goes unseen. The retry narrows the race but can't close it. Run `finding` calls one at a time, never in parallel.
- **Never into another in-flight run:** when runs go in parallel (see Parallel runs in `LOOP.md`, next to the `/factory` skill), a run never uses `--into` to fold a finding into an in-flight run's feature issue or any of its sub-issues, so two runs never write the same body. Within a run, `finding` calls stay one at a time. The [progress checklist](#progress-checklist) is only ever written by the run that owns that issue.
- **One comment:** once the item is saved, it posts a short comment on `#x` naming the reviewer, round, parent, and PR, then prints `~ #x merged <url>`.
- **Labels, blocker wins:** `#x` then gets the finding's review-type label, so it carries one type label per reviewer whose findings it holds, and its severity: a `blocker` adds `blocker` and removes `nit`; a `nit` adds `nit` only when `#x` has no `blocker`. `#x` never has both. A missing type label is warned about and skipped, as above. If the label write fails, the finding is already merged: run [`relabel`](#node-b-relabel-label-open-findings-by-severity-and-review-type) to repair it.
- **No new issue, no card move:** it never creates an issue, links a sub-issue, or calls `move`. `#x` stays in whatever column it's in.

## `node $B polish --milestone M`: find or create a milestone's Polish issue

`M` is `active`, `next` or an open milestone's exact title, found as [`milestone --resolve`](#node-b-milestone---json-print-the-active-and-next-milestones) finds it. Prints `= #x <url>` when the milestone has an open `from-review` issue titled exactly `Polish: <milestone title>`, and puts its card in Backlog if it has none on the board. Otherwise it creates one the way `finding` does, with no finding under its `## Merged findings`, labelled `from-review`, with its card in Backlog, and prints `+ #x created (polish) <url>`. `/factory groom` uses it to get a merge target that doesn't exist yet. An unknown milestone or a milestone error exits 1 with `✗`.

## `node $B backlog [--json]`: list open review findings

Lists every open issue labeled `from-review`, sub-issues included, so the orchestrator can triage a round's findings against them before filing.

- Without `--json`: a markdown table of issue, parent (for sub-issues), title, where, problem, and the number of merged findings. A problem longer than 120 characters is cut to 120, ending in `…`.
- `--json`: a JSON array, one object per issue, with the full problem text: `{ number, title, where, problem, fingerprints, merged, parent }`. `where` is the file from the `| Where |` row (no backticks or line number; `null` for `n/a`). `problem` is the `**Problem.**` text or `null`. `fingerprints` are every finding marker in the body. `merged` is the problem text of each merged item, without its `` `path:line`: `` prefix (a bare extensionless file with no line, like `` `Dockerfile`: ``, can't be told from an inline-code label and is kept). `parent` is the parent issue's number, or `null`.

## `node $B relabel`: label open findings by severity and review type

Labels every open `from-review` issue, including ones filed before these labels existed, from what its body records: the `| Severity |` row, the `` `reviewer-x` `` in the `| Found by |` row, and each generated `## Merged findings` item (`**nit** (ux, …)`). Hand-merged `**#n**` items add nothing. The same blocker-wins rule as [`--into`](#--into-x-fold-a-finding-into-an-existing-issue) applies, and type labels are only ever added.

- **Output:** one line per changed issue, like `~ #12: +blocker +security -nit`, or `✓ no labels changed`. Running it again changes nothing.
- An issue whose body records no severity and no reviewer is skipped. A missing type label gets one `⚠️` warning and is skipped; it's never created. A missing `blocker` or `nit` label fails with `run board.mjs ensure` before anything changes.
- It doesn't touch closed issues and writes no audit-log entry. Exit `0` done, `1` if any issue's labels couldn't be written (each one prints `⚠️ #n: labels not updated …`).

## `node $B intake [--json]`: list requests waiting for triage

Lists every **open issue that has no card on this board and isn't labeled `from-review`**, sorted by number. That's the intake queue for `/factory triage`. It includes issues without `needs-triage`, because filers without write access can't label, and issues labeled `needs-info`, so they can be triaged again once the filer answers.

- Without `--json`: a markdown table of issue, title, author, filer (`external` or `insider`), labels, and missing sections. `|` in a title is escaped; an empty queue prints one `(empty)` row. The **Missing** column lists the request-form sections the body lacks, or is blank when it has them all.
- `--json`: an array of `{ number, title, url, author, external, labels, needsInfo, missing }`. `external` is true unless the author's `authorAssociation` is `OWNER` or `MEMBER`. `missing` lists, in order, whichever of `Problem`, `Desired behaviour` and `Filed by` the body lacks. A section counts when a `##` or `###` heading names it (any case; `behavior` works too) and some text other than `_No response_` follows before the next heading. A non-empty `missing` suggests `needs-info`; it doesn't block `accept`.

## `node $B triage <n> <decision> [--into x] --summary-file F`: record a triage decision

Records one decision a human confirmed. `<decision>` is `accept`, `duplicate`, `reject`, or `needs-info`. `accept` takes an optional `--milestone M`, where `M` is `active`, `next` or an open milestone's exact title (found as [`milestone --resolve`](#node-b-milestone---json-print-the-active-and-next-milestones) finds it). Without it no milestone is set and the repo's milestones aren't read: the issue keeps the milestone it already has, if any. The summary file holds the restatement (accept), a note (duplicate), the reason (reject), or the question (needs-info). An `accept` restatement, for insiders and external issues alike, uses the request form's headings: `### Problem`, `### Desired behaviour` and `### Filed by`, each followed by text.

- **Checks first, writes nothing on failure:** the decision must be one of the four; `duplicate` needs `--into <x>`, a positive issue number other than `<n>` (and `--into` is refused for the other decisions); `--milestone` is refused for any decision but `accept`; the summary must not be empty, and an `accept` summary must have all three sections (the error names the missing ones). Then the issue must be open and must **not** already have a card on the board, and `#x` must exist. With `--milestone`, `M` must resolve: an unknown title, a missing active or next milestone, or a milestone error exits 1 before anything is commented, labelled, set, logged or moved.
- **Then, in order:**
  1. a comment that starts `### 🏭 Triage: <decision>`. For `accept` the summary goes between `<!-- factory:restatement -->` and `<!-- /factory:restatement -->` and the comment names `/factory <n>` as the next step and the milestone the issue is in, the one `--milestone` set or the one it already had (it says the issue is unscheduled only when it has none); `duplicate` says `Duplicate of #x`; `reject` and `needs-info` show the reason or the question;
  2. labels: `external` when the author isn't an `OWNER` or `MEMBER`; `accept` removes `needs-triage` and `needs-info`; `duplicate` and `reject` remove `needs-triage`; `needs-info` adds `needs-info`;
  3. `duplicate` and `reject` close the issue as `NOT_PLANNED` (with the link in the comment); `accept --milestone` sets the issue's milestone. A milestone that isn't set is a partial write, like a label failure: the log entry has `verified: false`, it exits 1 and the card isn't moved;
  4. one `triage` entry in the [audit log](#the-audit-log) (`#12: triage duplicate of #9`);
  5. `accept` ends with `move <n> Backlog --from none`, so the card appears in Backlog with its own move record.
- Exit codes: `0` done, `1` bad input or a partial write (the output says which), `2` bad usage.

## `node $B groom [--json]`: list the Backlog cards to groom

Lists every **open issue whose card is in Backlog**, grouped by milestone and sorted by number in each group, for `/factory groom`. It reads the repo's open milestones too.

- **Groups, in order:** the active milestone (its title and `Done when`), the next milestone, every other milestone that holds a Backlog card (by title; a closed milestone's cards are listed under its title, so none is dropped), then `Unscheduled (no milestone)`. Active and next appear whenever they exist, even with no cards. Every card is in exactly one group.
- Without `--json`: a heading per group (`### Active milestone: <title>`, `### Next milestone: <title>`, `### Milestone: <title>`, `### Unscheduled (no milestone)`), the active milestone's `Done when:` line, and a markdown table of issue, title, labels, age in days, source, and links. Source is `from-review (#<run>)` for a review finding (the parent issue, or the `#n` in its **Found by** row) or `request`. Links name the parent or sub-issues (every page of them), the `#n` items under `## Merged findings`, and any other `#n` the body mentions. No cards prints one `(empty)` row.
- **Polish issues:** a milestone's `Polish: <milestone title>` issue is listed after its group's other cards, or first when it has the `security` label. When a Polish issue's milestone is closed, a carry-forward line follows its group's table: `↪ #x: milestone closed; propose merge into Polish: <target>`, where the target is the active milestone, or else the next one, or `↪ #x: milestone closed; propose keep` when there's neither.
- `--json`: an array of groups, `{ group: 'active'|'next'|'milestone'|'unscheduled', milestone: { title, doneWhen }|null, cards }`, in the same card order, plus `carryForward: [{ number, decision: 'merge'|'keep', into: 'Polish: <target>'|null }]` on a group with a carry-forward line, where each card is `{ number, title, url, labels, ageDays, source, run, links: { parent, subIssues, merged, mentions }, milestone }` and `milestone` is its milestone's title or `null`.
- A milestone error (a broken `factory-milestone` block, two active or two next milestones, or a legacy active one with no `Done when:`) prints every error and exits 1.

## `node $B groom <n> <decision> [--into x] [--commit sha] --summary-file F`: record a groom decision

Records one decision a human confirmed. `<decision>` is `keep`, `merge`, `close-fixed`, `close-wont-do`, `split`, `next`, `schedule`, or `unschedule`. It **never moves a card**, so a card can't leave Done or enter a run column through it. The milestone forms are:

- `groom <n> schedule --milestone M [--swap x] --summary-file F`: put `<n>` in milestone `M`, resolved like [`milestone --resolve M`](#node-b-milestone---json-print-the-active-and-next-milestones): `active`, `next`, or an open milestone's exact title.
- `groom <n> unschedule --summary-file F`: take `<n>` out of its milestone.

- **Checks first, writes nothing on failure:** the decision must be one of the six; `merge` needs `--into <x>`, a positive issue number other than `<n>`; `close-fixed` needs `--commit <sha>`, 7 to 40 hex characters; no other decision takes `--into` or `--commit`; `schedule` needs `--milestone M`, and `--milestone` is refused for any other decision; `--swap <x>` is refused for any decision but `schedule`, and must be a positive issue number other than `<n>`; the summary must not be empty. Then `<n>` must be open with its card in Backlog.
  - `schedule`: `M` must resolve (an unknown title, a missing `active` or `next`, or a milestone error is refused), and `<n>` must not already be in it. **Active-scope rule:** when `M` is the active milestone, by keyword or by its title, the command needs `--swap <x>`, where `#x` is open, in the active milestone, with its card in Backlog, and not `<n>`; or a summary line `Blocks "Done when": <text>`. With neither it exits 1. `--swap` into any milestone that isn't active is refused.
  - `unschedule`: `<n>` must have a milestone.
  - **`next` rule:** `next` is accepted only when `<n>` is in the active milestone. Otherwise (another milestone, none, or no active milestone) it exits 1 with the hint `schedule it first: groom <n> schedule --milestone active`. For `merge`, `#x` must exist and be open, neither `#x` nor its parent may have a card in Spec, Ready, Build, Review, Approve or Needs human, and an `<n>` labelled `external` merges only into an `#x` labelled `external` (so its text stays fenced and its human gate stays).
- **Then, in order:**
  1. `merge` only: adds `- [ ] **#<n>** <summary>` under `## Merged findings` in `#x`, with `<n>`'s finding fingerprints as markers (read back and retried if lost). `<n>`'s title is never copied, since it may be untrusted text. If `#x` already lists `**#<n>**`, only the fingerprints it's missing are added; it counts as done only when every fingerprint is there. When fingerprints carry over and `#x` lacks the finding label (`from-review`), it's added so `finding` dedup still sees them. When fingerprints carry over, `#x` also gets `<n>`'s severities and review types, read from `<n>`'s body the way [`relabel`](#node-b-relabel-label-open-findings-by-severity-and-review-type) reads them, with blocker winning; a missing type label is warned about and skipped. Then it comments on `#x`, naming `#<n>` by number;
  2. `schedule --swap <x>` only: clears `#x`'s milestone (if that fails, nothing else is written to `#x` or `<n>`: no comment, labels or milestone; the `groom` entry is still logged with `verified: false` and the swap problem, and the command exits 1), removes `#x`'s `next` label, and comments `### 🏭 Groom: unschedule` on `#x`, naming `#<n>`. Once `#x` is cleared, a rerun of the same swap is refused, so the first later write that throws or errors (`#x`'s labels or comment, or `<n>`'s comment, labels or milestone) stops every write after it: the `groom` entry is still logged with `verified: false`, the swap, and a problem that says `#x` was already taken out of the milestone and gives the recovery, `gh issue edit <n> --milestone 'M'`, or put `#x` back with `gh issue edit <x> --milestone 'M'` and rerun (the title is single-quoted for the shell); the command exits 1;
  3. a comment on `<n>` that starts `### 🏭 Groom: <decision>`, names `#x` (merge), the commit (close-fixed), or the milestone and any swap (schedule, unschedule), holds the summary, and ends `<sub>factory-board · groom</sub>`;
  4. labels: `next` adds the `next` label; `merge`, `close-fixed`, `close-wont-do`, `unschedule`, and `schedule` into a milestone that isn't active remove it;
  5. `close-fixed` closes the issue as `COMPLETED`; `close-wont-do` and `merge` close it as `NOT_PLANNED`; `keep` and `split` only comment;
  6. `schedule` sets `<n>`'s milestone and `unschedule` clears it; a write that fails is a problem: the entry is unverified and the command exits 1;
  7. one `groom` entry in the [audit log](#the-audit-log) (`#12: groom merge into #9`, `#12: groom schedule into milestone v1 (swap #9)`, `#12: groom unschedule`).
- Exit codes: `0` done, `1` bad input or a partial write (the output says which), `2` bad usage.

## `node $B feature <n>`: print the feature text for writer-spec

The orchestrator gives writer-spec this text, never the raw issue body. Neither `triage` nor `feature` ever edits the issue body.

- **Insider** (`OWNER` or `MEMBER`) **with a restatement**: the latest restatement block, then `Original request from @<who> (insider):` and the original title and body as plain text.
- **Insider with no restatement** (never triaged, such as `/factory <feature>`, `/factory add`, or a review-finding card): the title plus the body.
- **External**: the latest restatement block written by a maintainer (`OWNER` or `MEMBER`; blocks in anyone else's comments are ignored), then the original title and body inside `<untrusted-issue-text>` … `</untrusted-issue-text>`. Any delimiter inside the original is defused, so it can't close the block early.
- **External with no restatement**: it fails (exit `1`). Triage the issue first.

## `node $B filer <n>`: print who filed an issue

Read-only. Prints one JSON object, `{ number, author, association, external }`. `association` is GitHub's `authorAssociation` (`OWNER`, `MEMBER`, `COLLABORATOR`, `CONTRIBUTOR`, `NONE`, …) and `external` is true unless it's `OWNER` or `MEMBER`. It exists because `gh issue view --json` has no `authorAssociation` field. The `/factory <n>` untriaged gate and `/factory add #<n>` use it. Exit `1` if the issue isn't found.

Read-only. Prints how many times `/factory revise` sent issue `<n>` back to Build: the number of verified `move` entries in the [audit log](#the-audit-log) from `Needs human` to `Build` for that issue (revise is the only thing that makes that move). The orchestrator adds it to `max_rework_rounds` to get the rework budget. It reads only the log, which agents can't write, so nothing in the build records (where builder replies land verbatim) can raise the budget.

## `node $B budget <n> [--round <r>] [--json]`: print the rework budget

Read-only. Prints the rework budget for issue `<n>` as a bare integer: `settings.max_rework_rounds` from `.eridanilabs/autofactory/board.json` (`3` when it's missing) plus [`revisions <n>`](#node-b-revisions-n-count-human-revisions), so only verified `Needs human → Build` moves in the audit log count. With `--round <r>` it adds a second line, `round <r>: rework allowed` when `r - 1 <` the budget, otherwise `round <r>: budget used up`. `--json` prints `{ issue, maxReworkRounds, revisions, budget }`, plus `round` and `mayRework` with `--round`. Exit `0` either way; the answer is in the output. A bad `<n>`, a `--round` that isn't a positive integer, a `max_rework_rounds` that isn't a non-negative integer, or a `size_limit` that isn't a positive integer exits `1` with `✗ …`.

## `node $B overlap <n> --check 1|2 [--json]`: check parallel runs for overlap

Read-only; it doesn't fetch, so run `git fetch origin` first. Runs the minimal overlap check from Parallel runs in `LOOP.md` (next to the `/factory` skill) for issue `<n>` against every in-flight card (Spec, Build, Review or Approve, other than `#<n>`; draft cards and Ready cards don't count). With nothing in flight it prints `ok` without calling `git`. A new feature has no issue yet when check 1 runs, so pass `new` as `<n>` there (check 1 only).

For each in-flight run `#<m>` it finds the branch `factory/<m>-*` (local or `origin/`; more than one is an error), reads it from `origin/<branch>` if that exists, otherwise the local `<branch>`, and takes its files as `git diff --name-only -z origin/main...<ref>` (NUL-separated, so names with special characters aren't quoted) plus the `## Likely files` in its spec, read from the fetched log branch at `origin/factory-log:runs/<m>-<slug>/spec.md`.

- **Check 1** (before Spec) blocks on `#<m>` with `no spec yet` when it has no branch or no readable `spec.md`, and with `touches protected paths` when its files include `.eridanilabs/autofactory/`, the old `factory/board.json`, `.github/skills/`, `.github/agents/`, `.agents/` or `.apm/`.
- **Check 2** (before Build, and on revise) does all of check 1, and also blocks with `shared paths` when `#<n>`'s own files (read the same way) share an exact path with `#<m>`'s, or with `touches protected paths` when `#<n>`'s own files are protected; that block names the first in-flight run. It's an error if `#<n>` has no spec while a run is in flight.

It prints `ok`, or one line per block: `blocked by #<m>: shared paths <a, b>`, `blocked by #<m>: touches protected paths <a, b>` or `blocked by #<m>: no spec yet`. A path that doesn't match `^[A-Za-z0-9._/-]+$` is shown as `(path withheld)`, so every line is safe to pass to `--reason`. `--json` prints `{ ok, blocks: [{ by, reason, paths }] }`, with paths withheld the same way. Exit `0` when ok, `3` when blocked, `1` on an error or a bad `<n>` or `--check`.

## `node $B stale <n>`: check a Ready card's spec against main

Read-only; it doesn't fetch, so run `git fetch origin` first. `/factory <n>` runs it on a Ready card, after overlap check 2 and before the `Ready → Build` move. It finds the run's branch `factory/<n>-*` as `overlap` does, reads `## Likely files` from `origin/factory-log:runs/<n>-<slug>/spec.md`, and lists each Likely file that changed on `origin/main` since `merge-base(<run ref>, origin/main)`: the run's branch has no commits before Build, so that merge-base marks when the spec was written. Paths match exactly, as in `overlap`.

It prints `ok` and exits `0` when none changed. Otherwise it prints `stale: <a, b>` (a path that isn't shell-safe is shown as `(path withheld)`) and exits `3`. A spec with no `## Likely files` can't be checked, so it prints `stale: no Likely files in spec` and exits `3` too. No branch (`✗ #<n> has no factory/<n>-* branch …`), no spec on the log branch (`✗ … run \`git fetch origin\` and retry`) or a bad `<n>` exits `1`.

## `node $B reviewers [--base <ref>] [--run <run>] [--json]`: pick the reviewers a change needs

Read-only; it doesn't fetch, so run `git fetch origin` first. It runs `git diff --name-only -z <base>...HEAD --no-renames` in the current directory (`<base>` defaults to `origin/main`; a rename lists both paths) and matches each changed path against the `reviewers` rules in [board.json](../../../apm_modules/eridanilabs/autofactory/.eridanilabs/autofactory/board.json). It reads those rules with `git show <base>:.eridanilabs/autofactory/board.json` (it falls back to `<base>:factory/board.json` when the base has only the old path): the base's copy, never the branch's, so a branch can't switch off its own reviewers. Each rule is `{ name, always?, paths, reason }`: an `always` reviewer is always selected, and any other is selected when a changed path matches one of its `paths` globs. In a glob, `*` and `?` stay within one path segment, `**/` matches zero or more directories, `{a,b}` is alternation, and matching is case-sensitive. Change the rules in `board.json`; no code change is needed. A change takes effect once it is on the base.

- **Always on:** `reviewer-code` and `reviewer-security` always run, whatever the rules say.
- **Fail safe:** a changed path that matches no rule, a failed diff or an empty diff selects every reviewer. So does a change to `.eridanilabs/autofactory/board.json` (or the old `factory/board.json`) or anything under `.apm/skills/factory-board/`, `.agents/skills/factory-board/` or `.github/skills/factory-board/`, which decide the selection.
- **No base rules:** if the base has no valid `reviewers` list (no file, bad JSON or no list), it falls back to this checkout's list and selects every reviewer in it, with a fail-safe reason.
- **`--run <issue>-<slug>`** reads `.eridanilabs/autofactory/runs/<run>/` (refresh it with [`records`](#node-b-records-run-mirror-a-runs-records)). A `Reviewers: +ux` line in its `spec.md` adds `reviewer-ux`; it can't remove one (`-code` is ignored). Every reviewer with a `review-<r>-<domain>.md` record there is kept, with the reason `ran in an earlier round`, so the set only grows within a run.
- **`--since <sha>`** (round 2+, needs `--run`): the orchestrator passes the round's `<last-reviewed-sha>`. It runs `git diff --name-only -z <sha>..HEAD --no-renames` and matches the rules only against that delta. `reviewer-code` and `reviewer-security` still always run, a reviewer whose `paths` match a delta file is selected, and a spec's `Reviewers: +x` still adds one. It reads the run's records from `origin/<logBranch>` (the base's `logBranch`, `factory-log` by default; it never fetches), listed and read with `git ls-tree` and `git show` as [`records`](#node-b-records-run-mirror-a-runs-records) does, never from the mirror, which the builder can write. Round `<r-1>` is the highest `review-<r>-*` record there. A reviewer whose latest record has a `[blocker]` finding line, or a verdict line (the first non-blank line after a leading `# Review r<r>: <domain> (<model>)` heading) other than `VERDICT: PASS`, or can't be read, has an open blocker. So does one that a `triage-<r>` record there (repeats like `triage-1.2.md` included) of its latest record's round names on a row with an `upgraded:` reason, or on a `[blocker]` row that wasn't parked (`park`) or `downgraded:`; a triage record that can't be read leaves every reviewer of that round open. Such a reviewer is selected with the reason `recheck its open [blocker] from round <r-1>`. Any other reviewer that ran before is skipped with the reason `no new changes in its domain since round <r-1>`, and a reviewer that never ran is still selected when its rules match the full diff `<base>...HEAD`. The fail-safes still apply to the delta and select every reviewer: a delta path under the selection paths above, a failed delta diff, a base with no valid rules, or a delta path no rule matches. An empty delta isn't a fail-safe: it selects only the required reviewers, the open-blocker ones and the spec's adds. A `<sha>` that doesn't match `^[0-9a-f]{7,40}$` exits `1` with `✗ …`. If `git merge-base --is-ancestor <sha> HEAD` fails, or the log branch can't be read or has no review record for the run, it falls back to the full-diff selection, and every reason ends with a `fall-back:` note that says so. The rules still come only from the base. When the delta is used, `--json` adds `since` after `base`, and `files` lists the delta's files; after a fall-back there's no `since`, and `files` is the full diff.

It prints one line per reviewer, `selected <reviewer>: <reason>` or `skipped <reviewer>: <reason>`, selected ones first. A path in a reason that doesn't match `^[A-Za-z0-9._/-]+$` is shown as `(path withheld)`. `--json` prints `{ base, files, selected: [{ reviewer, reason }], skipped: [{ reviewer, reason }] }`, with `files` withheld the same way.

Exit `0` even when the diff fails: every reviewer is selected, and the reason says the diff failed. Exit `1` with `✗ …` for a `--base` that starts with `-` or has a character outside `A-Z a-z 0-9 . _ / @ ^ ~ { } -`, a `--run` that isn't `<issue>-<slug>` or has no `spec.md` in its mirror, or a base with no valid `reviewers` list when this checkout's is missing or invalid too. On a non-zero exit, the orchestrator spawns every reviewer.

## `node $B size [--base <ref>] [--json]`: count a run's changed code lines

Read-only; it doesn't fetch, so run `git fetch origin` first. It runs `git diff --numstat -z <base>...HEAD --no-renames` in the current directory (`<base>` defaults to `origin/main`; a rename counts as a delete plus an add) and adds up the added and removed lines of every changed file, except:

- markdown, at any depth: a file name ending in `.md` or `.markdown`, in any case (`.mdx` counts)
- unit tests, at any depth: a file under a `test/`, `tests/` or `__tests__/` directory, or a file name `<stem>.test.<ext>`, `<stem>.spec.<ext>` or `<stem>_test.<ext>` (`src/test.js` and `src/testing.js` count)
- the lockfiles `package-lock.json`, `npm-shrinkwrap.json`, `yarn.lock`, `pnpm-lock.yaml` and `apm.lock.yaml`, at any depth
- an installed copy whose `.apm/` source changed in the same diff: `.agents/skills/<p>` when `.apm/skills/<p>` changed, and `.github/agents/<f>` when `.apm/agents/<f>` changed (it's then `apm install` output). Any other installed file counts.

It prints `<lines> changed code lines, limit <limit>: over the limit` (or `within the limit`), where the limit is `settings.size_limit` from the base's `board.json` (`git show <base>:.eridanilabs/autofactory/board.json`, or the old `<base>:factory/board.json` as a fallback, as for `reviewers`), never the branch's, committed or in the working tree, so a run can't raise its own limit. It's `400` when the base has no `board.json`, no `settings` or no `size_limit`. `size` reads nothing from where the script sits, so the orchestrator runs the base's copy from `.workbench/`. A count is over only when it's greater than the limit. A binary file adds 0 lines, but git can be made to treat a code file as binary (a `.gitattributes` line or a NUL byte), so a binary file outside the excluded paths, or a changed `.gitattributes` anywhere, makes it over the limit whatever the count, and the line ends with the reason, for example `3 changed code lines, limit 400: over the limit (binary files outside the excluded paths: src/a.js; .gitattributes changed: .gitattributes)`. `--json` prints `{ lines, limit, over, binary, gitattributes }`. A path that doesn't match `^[A-Za-z0-9._/-]+$` is shown as `(path withheld)`. The orchestrator gives the output to approver-merge, which escalates when it's over the limit or the count is missing. Exit `1` with `✗ …` for a bad `--base` (as for [`reviewers`](#node-b-reviewers---base-ref---run-run---json-pick-the-reviewers-a-change-needs)), a base git can't diff, a base `board.json` that isn't valid JSON, or a base `size_limit` that isn't a positive integer.

## `node $B size <n> --est <lines> [--notes-file F]`: record a card's size estimate

Triage and groom run it for each card they accept or review. `--est` is the estimated code lines the change will add and remove (a non-negative integer; anything else exits `1` with `✗ …`). The notes file lists the behaviours the card asks for, one line starting with `- ` each; with no file the count is 0, and the note says `Behaviours: none listed.`; a file that doesn't exist exits `1` with `✗ --notes-file <f> not found`. It computes `score = est + 25 × max(0, behaviours − 4)` and writes one block into the issue body:

```markdown
<!-- factory:size est=<lines> unit=code-lines behaviours=<k> score=<s> -->
### Size estimate
Estimate: <lines> code lines. Score: <s> (estimate + 25 per behaviour past 4), limit <limit>: within the limit.
Behaviours (<k>):
- <behaviour>
<!-- /factory:size -->
```

Only that exact block counts, with its opener and closer each on a line of their own: an opener quoted in the prose, or one left unclosed, is user text and is kept. Run again, it replaces the block in place, so a body never holds more than one marker, and the rest of the body is left byte for byte. When the score is over `settings.size_limit` (from this checkout's `board.json`), it adds the `needs-split` label, and at or under the limit it removes it, changing the labels only when needed. `needs-split` is one of the default labels, so `ensure` creates it; it exits `1` asking for `ensure` when the label is missing. `size <n>` without `--est`, or `--est` without `<n>`, is a usage error (exit `2`). It prints `✓ #<n>: score <s> (est <lines>, <k> behaviours), limit <limit>: over the limit, added needs-split` (or `within the limit`, `removed needs-split`). When the body it replaces already had a size block, the line ends with `; was score <s0> (est <e0>)`, the earlier block's numbers; with no earlier block the line is unchanged. The earlier block is read from the body each write actually replaces, so another writer's change in between is accounted for; a rerun after `size block saved, but needs-split not updated` reports the block its own earlier run wrote. Run step 2 uses it to tell the spec's estimate from the earlier one.

## `node $B record <run> <name> --body-file F`: add a run record

`<run>` is `<issue>-<slug>`, like `12-clear-completed`. Every record of a run lives on the [audit log](#the-audit-log) branch, in `runs/<run>/`, never on `main` or the run's branch. `record` adds the text of file `F` there as `<name>.md`, in one commit (`chore(factory): <what> for #<issue>` with a `Refs: #<issue>` footer), and prints `+ runs/<run>/<file> <url>`, where `<url>` links the record at that commit.

| `<name>` | Message | Again? |
|----------|---------|--------|
| `spec` | `add spec` | no |
| `build-<r>` | `record build round <r>` | no |
| `review-<r>-<domain>` | `record review round <r>` | no |
| `triage-<r>` | `record triage round <r>` | yes |
| `revise-triage-<r>` | `record revise triage` | no |
| `revision-<r>` | `record human revision` | no |
| `approval` | `record approval` | yes |
| `approval-human` | `record human approval` | yes |
| `needs-human` | `record escalation` | yes |
| `rejection` | `record rejection` | yes |

A record is written once: a second `spec` or `build-<r>` for the same run fails (exit `1`, `… already exists; records are written once`). One that can be written again gets the next free numbered name instead (`needs-human.md`, `needs-human.2.md`, …). Any other name, an empty file, or a `<run>` that isn't `<issue>-<slug>` fails too.

It never touches a checkout's branch, index or working tree, apart from the mirror below. It fetches the log branch, builds the commit on its tip with a temporary index, and pushes it as a fast-forward. If another writer moved the branch in the meantime, it starts again from the new tip (up to 4 tries). It also writes the record into this checkout's mirror, `.eridanilabs/autofactory/runs/<run>/`.

## `node $B records <run>`: mirror a run's records

Fetches the log branch and replaces `.eridanilabs/autofactory/runs/<run>/` in this checkout with a copy of `runs/<run>/` from it, then prints `✓ <count> records in .eridanilabs/autofactory/runs/<run>/: <files>`. The folder is git-ignored: `record` and `records` give `.eridanilabs/autofactory/runs/` its own `.gitignore` of `*`, so it stays out of git even in a repo whose `.gitignore` still has only the old `.factory/` line. It's where the orchestrator and its agents read the records (`RUN` in the `/factory` skill). Because it's replaced each time, a file written there by anything else is gone after the next `records`, so it can't pass for a record.

## `node $B merge <n> <p> [--pre-check]`: check and merge a run's PR

The `/factory` orchestrator's **Merge** section runs it twice, in the run's checkout (its worktree, or the primary checkout for a pre-change run): `--pre-check` as step 1, then the CI check, then without the flag as step 3. Every git, gh and test call takes its arguments as an array, with no shell, so the branch name is always a plain argument.

Both forms first read the PR with `gh pr view <p>` and refuse, before any git command, a PR from a fork (`isCrossRepository`), a head branch that doesn't match `^factory/<n>-[a-z0-9]+(-[a-z0-9]+)*$`, or a PR whose `baseRefName` isn't `main` (`PR doesn't target main`: `gh pr merge` merges into the PR's own base, but the check runs against `origin/main`). Then they refuse a checkout that isn't clean or isn't on that branch. The same read takes the PR's `state` and `headRefOid`: a PR that's already `MERGED` (a rerun after a crash) is never readied, merged, rebased or pushed again, and counts only from the run's own checkout (clean, on that branch) with `HEAD` at its `headRefOid`. Then `--pre-check` prints `✓ PR #<p> already merged` and exits `0`, and the merge goes straight to reading the sha and the cleanup. Any other `MERGED` PR (a wrong or stale PR number, or a rerun after the cleanup started) is refused as `checkout doesn't match the PR` before its sha is read or any branch is touched.

- **`--pre-check`** records `L` (`git rev-parse HEAD`) before `git fetch origin`. If `origin/main` isn't an ancestor of `HEAD`, it rebases onto it, pushes with `--force-with-lease=refs/heads/<branch>:<L>`, and runs `settings.test_command` from `.eridanilabs/autofactory/board.json` (`npm test` when it's missing), split on whitespace and run without a shell. Its output goes only to the log file, and a failure prints `✗ tests failed`: the log file shows why, including a `test_command` that isn't on PATH. Otherwise it changes nothing, but refuses with `push refused` if `origin/<branch>` isn't at `HEAD`, so a rebased head left local by an earlier refused push never passes. Because `L` is pinned before any fetch, the push is refused when the remote branch isn't at `L`, even after a fetch from another checkout has moved `origin/<branch>`. A rebase conflict runs `git rebase --abort`, so `HEAD` is back at `L`. On success it prints `✓ pre-merge check <short sha>`.
- **Without `--pre-check`** it never fetches, rebases or pushes before the merge. It runs `gh pr ready <p>`, then `gh pr merge <p> --squash --match-head-commit <local HEAD sha>`, never with `--delete-branch`. Then it reads the PR's `state` and `headRefOid`, and goes on only if it's `MERGED` with the head it asked to merge. If `gh` failed and it isn't, it reads the queue once, waits as below for a PR that's `OPEN` and in the merge queue (a rerun after it was queued), and refuses any other with `merge refused`. If `gh` succeeded and the PR is in the merge queue (a required merge queue only queues it), it waits: every 30 seconds, for up to 60 minutes, it reads the PR's `state`, `headRefOid` and `isInMergeQueue` with `gh api graphql`, and goes on once the PR is `MERGED` with that head. A failed first read is tried once more after 30 seconds. When it first sees the PR queued, the CLI prints `… queued, waiting for the merge queue` to stderr, then little else for up to 60 minutes. A PR that leaves the queue without merging exits `1` with `removed from merge queue: <reason>`, the reason of a removed-from-merge-queue event newer than the one seen at the first queued read, printed only if it matches `^[A-Za-z0-9 ._()/-]{1,120}$` and as `(reason withheld)` otherwise (the full reason goes to the log). A closed PR's reason is `PR closed`. An open PR with no new event is read once more: `MERGED` with that head goes on as a merge, and anything else is `(no reason recorded)`. A PR still queued after 60 minutes exits `1` with `merge queue timed out`, and its branch stays in the queue. A PR that `gh` merged without error but that isn't merged and isn't in a queue is `merge not completed`. None of these cleans anything up, and each goes to Needs human, never Done. Without a merge queue, nothing waits. It reads `mergeCommit.oid` from `gh pr view <p>` and prints `✓ merged PR #<p> as <short oid>`, even when `origin/main` has moved on. Then it cleans up. It never switches to `main` or pulls it, in any checkout: Run from a run's worktree, it runs the following in the primary checkout (the first entry of `git worktree list`): `git worktree remove <worktree>`, then `git branch -D <branch>`, then deletes the remote branch as below, then `git fetch origin`, and the primary checkout's `HEAD` stays where it was. Run from the primary checkout itself (a pre-change run, started before every run got its own worktree), it leaves that checkout's `HEAD` and branch alone, deletes only the remote branch as below, and exits `4` with `cleanup incomplete`, since the local branch is left for the user to delete. `/factory` never pulls the local `main`, so `main` may be behind `origin/main` until the user pulls it. The remote delete runs `git push --force-with-lease=refs/heads/<branch>:<merged head> origin --delete refs/heads/<branch>` only when `git ls-remote --exit-code --heads origin refs/heads/<branch>` lists exactly that ref: `ls-remote` matches the end of a ref name, and the full name can't resolve to a tag. The lease refuses the delete (`cleanup incomplete`) if anyone pushed to the branch after the merge.

Raw git, gh and test output goes only to a log file in a temp directory. The command prints that file's path (`  log: <path>`), and otherwise only its outcome, shas and one fixed reason. The log holds raw output from the PR's own code: the `/factory` skill's **Merge** section says what of it may go into a comment.

| Exit | Prints | Means |
|------|--------|-------|
| `0` | `✓ pre-merge check <sha>`, `✓ PR #<p> already merged` (`--pre-check`) or `✓ merged PR #<p> as <sha>` | done |
| `1` | `✗ PR couldn't be read`, `✗ PR is from a fork`, `✗ branch name not allowed`, `✗ PR doesn't target main`, `✗ checkout doesn't match the PR`, `✗ fetch failed`, `✗ rebase conflict`, `✗ push refused`, `✗ tests failed`, `✗ merge refused`, `✗ merge not completed`, `✗ removed from merge queue: <reason>` or `✗ merge queue timed out`, or `` ✗ board.json `settings…` `` when `settings` isn't an object, `max_rework_rounds` isn't a non-negative integer, `size_limit` isn't a positive integer, or `test_command` is empty or not a string, all before any git or gh call | not merged by this call (a refused PR may have merged earlier) |
| `2` | the usage text | a bad `<n>` or `<p>`, or an option other than `--pre-check` |
| `4` | `✓ merged PR #<p> as <sha>`, or `✓ merged PR #<p>` with no sha, then `✗ merge commit not read` and/or `✗ cleanup incomplete` | merged, but the merge sha or the cleanup is missing |

Like every command but `init`, it first checks that `board.json` targets this checkout's `origin`, and passes that repo to `gh` as `--repo`.

## `node $B milestone [--json]`: print the active and next milestones

Reads the repo's open milestones and the board's cards, and prints the active and next milestones (the factory skill's LOOP.md says how they're found: each milestone's `factory-milestone` JSON block, or the deprecated `Status:`/`Done when:` lines). Each has its title, its `Done when`, its open and closed issue counts, and its Backlog cards (number and title). A card whose issue has the `external` label prints as `#<n> (external; title withheld)` instead: an outside filer wrote that title and can still edit it. Then it prints how many Backlog cards are unscheduled (have no milestone), then one `⚠` line per warning: a milestone that still uses the deprecated lines (`⚠️ milestone "<title>" uses deprecated Status:/Done when: lines; use a factory-milestone block`), an active milestone with no next, more than two later milestones (open, and `planned` or with no status), or an epic in the active milestone whose open sub-issues are unscheduled or in another milestone (it reads the active milestone's open issues and their sub-issues, every page). Warnings never change the exit code. `--json` prints the same data as `{ schemaVersion, active, next, unscheduled, warnings }`, with `null` for a missing milestone, `number` (the GitHub milestone number) and `schemaVersion` (the block's, or `null` for legacy lines) on each milestone, and each Backlog card as `{ number, title, external }` (the title isn't withheld there, so fence it when `external` is true); it reads every page of open milestones and fails closed, as [docs/board-reads.md](../../../apm_modules/eridanilabs/autofactory/docs/board-reads.md) says. With no active milestone it says so and still exits 0. A broken `factory-milestone` block (bad JSON, a missing or wrong `schemaVersion`, a bad `status`, an unknown key, an active one with no `doneWhen`, or two blocks), two active (or two next) milestones, or a legacy active one with no `Done when:` line, prints every error, each naming its milestone, and exits 1.

`milestone --issue <n>` reads issue `<n>`'s milestone and the open milestones, for `/factory <n>`'s start-up. When an active milestone exists and `<n>` isn't in it, it prints one line, `⚠ #<n> is outside the active milestone "<active>" (in "<other>" | unscheduled); running anyway`; otherwise (no active milestone, or `<n>` is in it) nothing. It exits 0 either way. When the milestones can't be read (two active ones, say), it prints `✗ <error>` and still exits 0, as `status` does. An `<n>` that isn't a positive number, or an issue that isn't found, prints `✗ <error>` on stderr and exits 1. It takes no `--json` or `--resolve`, and writes nothing.

`milestone --resolve M` reads only the open milestones and prints the one title `M` names, then exits 0. `active` and `next` are keywords (they win over a milestone literally titled so) and name the milestones above, so their errors still apply; anything else must be an open milestone's exact, case-sensitive title. An unknown title, or `active` or `next` with no such milestone, prints `✗ <error>` and exits 1. It writes nothing. `/factory add --milestone` runs it before `gh issue create`.

## `node $B milestone set <number> --status S [--done-when T]` and `node $B milestone advance [--next <n>] [--force]`: change milestones

The two commands that write milestones, so a person (or a caller acting for one) never edits a description by hand. Run them only when a person asks. `<number>` and `--next <n>` are GitHub milestone numbers: the last part of the milestone page's URL (`…/milestone/<number>`), or list every open one with `gh api repos/<repo>/milestones --jq '.[] | [.number, .title]'`. `milestone --json` shows only the active and next ones' numbers. Both read the open milestones, check the whole change, and refuse with `✗ <problem>` and exit 1 before any write.

- **`milestone set <number> --status active|next|planned [--done-when "<text>"]`** rewrites only the open milestone's one `factory-milestone` block to `{ "schemaVersion": 1, "status": …, "doneWhen": … }`. The rest of the description stays byte for byte. `doneWhen` is the `--done-when` text, or else the milestone's current one (from its block or its legacy `Done when:` line). A description with no block (legacy lines or none) gets a new block appended, and its text is kept. It refuses a missing or bad `--status`, a milestone that isn't open, a description with more than one block, and a result with two `active` or two `next` milestones, an `active` one with no `doneWhen`, or any other milestone error.
- **`milestone advance [--next <n>] [--force]`** closes the active milestone, then rewrites next's block to `active` (keeping its `doneWhen`), then, with `--next <n>`, rewrites `<n>`'s block to `next`. The closed milestone's block is left as it is. It refuses when there's no active milestone, when the active one has open issues and there's no `--force` (the message gives the count), when next has no `doneWhen`, or when `<n>` isn't an open milestone other than the active and the current next. With no next milestone, it still closes the active one (and applies `--next`), prints `⚠ no active milestone: …` and exits 0. The order means a failure partway leaves no active milestone, never two.
- **`milestone advance --after <n>`** is what `/factory` runs after a merge moves `#<n>` to Done. It reads `#<n>`'s milestone with the open milestones. When `#<n>` has no milestone or isn't in the active one, it prints `skip: #<n> is not in the active milestone`; when the active milestone still has open issues, it prints `skip: active milestone "<title>" has <k> open issue(s)`. Either way it makes no write, logs nothing and exits 0. Otherwise it does what plain `milestone advance` does, with the same refusals, and its `milestone` entry also carries `issue: <n>`; its line ends `, after #<n>`, plus `, ⚠ no active milestone` when nothing was promoted. `--after` can't be combined with `--force` or `--next`: either is a usage error that prints `✗ --after can't be combined with …` and exits 1 before any read.

Each write is a REST `gh api -X PATCH repos/<repo>/milestones/<n>` (`-f state=closed` or `-f description=…`). After writing, it re-reads the open milestones and checks each one shows what was written, then appends one `milestone` entry to the [audit log](#the-audit-log). It prints `✓ milestone #<n> "<title>": set <from> → <to>` or `✓ milestone #<n> "<title>": advance, closed, promoted #<m>, next #<k>`. The re-read also runs the usual milestone checks on the whole list, so a change made at the same time that leaves two active or two next milestones, or an active one with no `doneWhen`, counts as a failure. When a write or the re-read check fails, the line starts `⚠️` and ends ` (partial)`, then it prints `✗ <what failed>`, then `Finish by hand:` and the exact, shell-quoted `gh api -X PATCH …` command for each write still missing, logs the entry with `verified: false`, and exits 1. If every write was made but the re-read check still fails (for example a change made at the same time), it says so under `Finish by hand:` and points to `milestone set`. Each command is a PATCH, so running one that already took effect is safe. A failed log entry alone prints `✗ not logged: <error>` and the entry's JSON, with no `Finish by hand:` lines, since every write was made. `--force` and `--after` are accepted only by `milestone advance`, and `--status` and `--done-when` only by `milestone set`; with any other command they're a usage error: it prints `✗ --force is only for milestone advance` (or the same for the other flag) and the usage, and exits 2 (`refresh` exits 1).

## `node $B status [--json]`: print the board

A markdown table of status, issue, title, agent, and checkpoint, in column order. Between the board URL and the table, it prints `Active milestone: <title> (<closed> of <total> closed)`, or one `✗ <error>` line per error when the milestones have errors (still exit 0). With no active milestone, there's no such line.

`--json` prints a versioned read of every card for other tools: `{ schemaVersion, repo, project, columns, items }`, with each item's type, repo, number, title, state, column, labels, milestone, parent, agent and checkpoint, in the order the Project returns them. It reads every page of items and labels. On any error it prints nothing to stdout, writes `✗ <error>` to stderr and exits 1. [docs/board-reads.md](../../../apm_modules/eridanilabs/autofactory/docs/board-reads.md) documents the fields.

## `node $B next [--json]`: the confirmed build order

The open issues labelled `next` that have a card on the board, in two lists. The ordered list holds each card whose latest verified `groom <n> next` entry in the audit log hasn't been undone by a later verified `merge`, `close-fixed`, `close-wont-do`, `schedule` or `unschedule` of it, or by another card's `schedule --swap <n>`. It's in the order those `next` entries were logged, oldest first, so it's the order a person confirmed them. Every other open `next` card, labelled or put back by hand, is listed under `Unconfirmed (labelled by hand):`, by number. A card is never in both lists, and never left out.

Without `--json` it prints the ordered cards numbered (`1. #12 <title>`), then the unconfirmed ones. `--json` prints a versioned read for other tools: `{ schemaVersion, repo, ordered, unconfirmed }`, each card `{ number, title, milestone, column }`, and each ordered one also with `confirmedAt`. It reads the board as `status --json` does, and the whole log. Both fail closed: on a GraphQL or `gh` error, a log branch with no `log/` tree, a log file GitHub can't return whole, or a log line that isn't JSON, it prints nothing to stdout, writes `✗ <error>` to stderr and exits 1. [docs/board-reads.md](../../../apm_modules/eridanilabs/autofactory/docs/board-reads.md) documents the fields.

## The audit log

Issue comments can be edited or deleted, and a project card keeps no history of its fields. So every board event is also a commit on **`factory-log`**, an orphan branch holding only the log and the run records, never code:

- `log/YYYY-MM.jsonl` has one JSON object per line: `ts`, `event` (`move`, `drift`, `triage`, `groom`, `milestone`, or `board`), `issue`, `title`, `from`, `to`, `agent`, `checkpoint`, `humanRequest`, `reason`, `next`, `pr`, `auto` (`github` or `fallback`, on Done only), `actor`, and `verified`. A `triage` entry has `decision`, `into` (duplicates), `milestone` (on `accept`: the title `--milestone` set, or the milestone the issue already had; left out when it has none), `external`, and `closed` instead of the move fields. A `groom` entry has `decision`, `into` (merge), `commit` (close-fixed), `milestone` (schedule: the milestone set; unschedule: the one cleared), `swap` (schedule `--swap`: the `#x` unscheduled), and `closed`. A `milestone` entry has `action` (`set` or `advance`), `milestone` (the number set, or the active one advance closed), `title`, `from` and `to` (the statuses; `active` → `closed` for advance), `closed`, `promoted` and `next` (advance: the numbers closed, promoted to active and made next), `actor` and `verified`. Summaries aren't logged.
- Each event is one commit (`#4: Build → Review`), so `git log --oneline origin/factory-log` reads like a changelog.
- A repo ruleset blocks deleting or force-pushing the branch, so history can only grow.
- Writes use `createCommitOnBranch` with the branch head they expect, so two writers can't overwrite each other. A loser re-reads and retries.
- `drift` records a refused move (a person moved the card). `board` records what `ensure` changed.
- `runs/<issue>-<slug>/` holds each run's [records](#node-b-record-run-name---body-file-f-add-a-run-record): its spec, builds, reviews, triage tables and decisions. Rejected runs keep theirs too.

`node $B log [issue]` prints the log as a table, for one issue or all of them.

## Rules

- **One card per feature, never one per stage.** The PR links to the issue (`Closes #n`). It doesn't get its own card.
- **Every move goes through `move`.** It's the only path that leaves a verified record, writes the audit log, and keeps the card's Status and fields verified.
- **Never rewrite `factory-log`.** It's append-only. Only `board.mjs` writes it (`move`, `triage`, `groom`, `ensure` and `record`). Don't push to it yourself, rebase it, or delete it.
- **A human drag is a signal, not permission.** On exit `3`, stop that feature and tell the user where the card is. Don't force it back.
- **`Done` means merged, or closed unmerged when labeled `rejected`, and GitHub moves it.** Call `move … Done` only after `gh pr merge` succeeds, with the merge commit as the checkpoint, or after `/factory reject` has closed the PR unmerged and the issue as not planned (`move <n> Done --from "Needs human"`). It records GitHub's move; it doesn't make its own unless GitHub is late.
- **Cards leave `Needs human` through `/factory approve`, `revise`, or `reject`.** `revise` moves the card back to Build (`--from "Needs human"`), `approve` merges it to Done, and `reject` closes it unmerged to Done. `/factory stop <n>` sends a running card (Spec, Build, Review or Approve) to Needs human between stages through the `factory:stop` label, or straight away with `--orphaned`.
- **`Backlog` holds parked work.** Cards get there through `finding --as backlog`, `/factory add`, or `triage <n> accept`, and leave through `/factory <issue#>`. A finding that belongs with an open card is folded into it with `finding --into <x>` instead of getting a card of its own. `/factory groom` reviews it through `groom`, which comments, labels and closes but never moves a card.
- **Untriaged requests stay off the board.** There's no Triage column: `intake` finds them, a human confirms each `triage` decision, and only `accept` puts a card on the board.
- **`Needs human` always carries a request.** Post the question as a comment first, then pass its URL as `--human-request`. Clear it (`--human-request ""`) when the card leaves.
- If `gh` lacks the `project` scope, stop and ask the user to run `gh auth refresh -s project`. Never ask for a token.
